## Ошибки, подтвержденные в тестовой базе

### 1. Высокий приоритет: повторная выдача уже выданного мешка

Источник: `addons/cabochon_manufacturing/models/material_transfer.py`,
`_validate_before_manager_confirm()` и `_confirm_issue()` (строки 445 и 546).

Воспроизведение обычными ролями: менеджер создает две самостоятельные выдачи
одного мешка 100 г разным работникам и подтверждает обе. Первый работник
принимает свою выдачу, затем второй принимает свою. Оба документа получают
`confirmed`, в журнале суммарно выдано 200 г, текущий вес мешка остается
100 г, владельцем становится второй работник.

Блокировка строки мешка присутствует, но после нее проверяется достаточность
веса без повторной проверки состояния, склада, владельца и резерва.
Нужна проверка актуальной доступности непосредственно перед проведением под
блокировкой. Самостоятельные выдачи также должны учитывать резерв заявок.

### 2. Высокий приоритет: сдача создает вес без исходного материала

Источник: `addons/cabochon_manufacturing/models/material_transfer.py`,
`_validate_before_manager_confirm()`, `_confirm_receipt()`,
`CabochonMaterialTransferLine._validate_amounts()`.

Менеджер создает через ORM сдачу без заявки и без `lot_id`, задав входной и
годный вес 100 г. После подтверждения менеджером и работником появляется
новый мешок 100 г без списания исходного материала. У ролей есть ACL на
создание документов и строк; ограничений формы недостаточно для RPC.

Нужно требовать реальный источник для ненулевой производственной сдачи и
проверять связь с подтвержденной выдачей, назначенным работником и заявкой.
Внешний приход уже имеет отдельный мастер и не должен подменяться сдачей.

### 3. Высокий приоритет: частичная помывка закрывает заявку с остатком

Источник: `addons/cabochon_manufacturing/models/material_transfer.py:776`.

Выдано 100 г на барабанную помывку. Сдача 40 г с `is_final_receipt=False`
приводит к `request.state='done'`, хотя у работника остается 60 г.
Следующая сдача не создается. Причина: помывка закрывает заявку независимо
от признака окончательной сдачи.

Код расходится с общим правилом частичных сдач в `docs/BUSINESS_RULES.md`.
Если помывка должна быть только окончательной, это следует явно закрепить
и запрещать частичную сдачу до проведения. Иначе нужен обычный переход
`partially_done` и следующая сдача. Закрытие с положительным остатком
должно блокироваться во всех путях, включая автоматический.

### 4. Высокий приоритет: отмененная заявка допускает выдачу

Источники: `addons/cabochon_manufacturing/models/production_request.py:734`
и подтверждения в `material_transfer.py`.

После подтверждения заявки создается выдача. Отмена заявки снимает резерв,
но выдача остается действующей. Менеджер и работник могут ее подтвердить:
заявка остается `cancelled`, мешок становится `issued`, появляется движение.
Это также создает конфликт с новой заявкой, которая может занять снятый резерв.

Нужно согласовать отмену с зависимыми документами и проверять состояние
заявки при обоих подтверждениях. Отдельно проверить гонку отмены и приемки.

### 5. Высокий приоритет: обход правила «несколько мешков только для труб»

Источники: `addons/cabochon_manufacturing/models/production_request.py`,
`_check_request_values()`, `CabochonProductionRequestSourceLine.create/write()`.

Создана заявка на помывку с одним мешком. Отдельный вызов `create()` модели
дополнительных источников добавляет второй мешок. Подтверждение заявки
успешно создает выдачу с двумя строками для `tumble_wash`.

Проверка родителя не вызывается при таком изменении дочерней записи.
Нужно перепроверять полный состав источников при изменении строк и перед
подтверждением, включая маршрут, период добычи и исключение мешков брака.

### 6. Средний приоритет: панель технолога занижает план для нескольких мешков

Источник: `addons/cabochon_manufacturing/models/cabochon_reports.py:62`.

Заявка на трубы: основной мешок 100 г, дополнительный 200 г.
`total_planned_weight_g=300`, но панель показывает `planned_weight_g=100`.
SQL суммирует только план основного мешка. Следует использовать общий
плановый вес и проверить остальные отчеты/экспорт с этим показателем.

### 7. Средний приоритет: ручной запуск ожидающей операции завершается ошибкой

Источник: `addons/cabochon_manufacturing/models/production_request.py:1308`.

`action_start()` ожидающей операции при пустом `request.started_at` пытается
записать защищенную дату заявки напрямую. Вызов от администратора завершается
`UserError: Статус и даты заявки меняются только через производственные действия.`
Кнопка «Начать» видима для ожидающей операции в отдельной форме маршрута.

Нужно определить допустимые состояния заявки для ручного старта, согласовать
кнопку с ними и использовать штатный переход. Простое отключение защиты даты
нарушило бы правило фактического старта после приемки материала.

## Другие замечания и рекомендации

1. **Безопасность обслуживания.** В README есть команды с буквальным паролем
   БД, а `install_modules.ps1` по умолчанию выбирает `Prod`. Удалить пароль
   из примеров, проверить его использование вне репозитория, сделать целевую
   базу обязательным параметром. Для рабочей базы предусмотреть явный режим
   обслуживания. Текущий скрипт уже делает бэкап и оставляет сервис остановленным
   при ошибке; эти свойства следует сохранить.
2. **Регрессионное покрытие.** Добавить тесты на все ошибки выше, прямые вызовы
   дочерних моделей, самостоятельные документы, смену доступности между двумя
   подтверждениями и гонку отмены с выдачей. Существующие 12 тестов проходят,
   но перечисленные нарушения не обнаруживают.
3. **CI.** `.github/workflows/static-checks.yml` проверяет Ruff, синтаксис Python
   и XML. Добавить чистую установку Odoo с регрессионными тестами и отдельный
   прогон миграций на обезличенной старой базе. Зафиксировать версии инструментов.
4. **Интерфейс.** `static/src/scss/list_columns.scss` применяет `max-content`,
   `nowrap` и `!important` ко всем спискам Odoo. В Playwright таблица заявок
   шириной около 1778 px при окне 1036 px. Ограничить стили нужными экранами,
   второстепенные колонки скрыть по умолчанию, проверить узкий экран работника.
5. **Контроль целостности.** Расширить диагностику: выдача по отмененной заявке,
   повторная выдача одной массы, сдача без источника и сверка остатка с движениями.
   Текущий отчет содержит полезные проверки, но не является полной сверкой баланса.
6. **Компании.** Документы разделены глобальными правилами, но складские зоны
   общие и имеют одного менеджера; журнал аудита не имеет `company_id`.
   Перед использованием нескольких компаний определить, какие справочники,
   менеджеры и аудиторские записи должны быть общими, затем проверить роли.
   Полная изоляция многокомпанейской среды этим обзором не подтверждена.
7. **Рост данных.** Обход родословной мешков и поиск движений выполняются для
   каждого мешка. Оценить число SQL-запросов и время на реалистичном объеме,
   затем пакетировать чтения там, где измерения покажут проблему. Нагрузочный
   тест в этом обзоре не выполнялся.
8. **Отчеты о качестве.** Сохранить явное указание базы процентов по заявке.
   Для общих KPI согласовать взвешенный процент от суммарной массы и среднее
   процентов отдельных заявок: это разные показатели. Расчетные величины
   не следует представлять как самостоятельный входной вес каждой операции.
9. **Начальная настройка.** Полезна проверка готовности: пользователи связаны
   с сотрудниками, зоны имеют ответственных, работники имеют допуски, заполнены
   справочники и нормы. Это уменьшит число ошибок при первом рабочем запуске.
10. **Этикетки.** QR/Code128 скрыты намеренно по прежнему решению, это не новая
    ошибка. Перед включением сканирования согласовать формат этикетки и проверить
    реальные печать/сканер. PDF и физическая печать в этом обзоре не проверялись.
