# Cabochon Odoo

Кастомизация Odoo 19 Community для учета изготовления кабошонов: мешки камней,
складские зоны, операции, заявки, выдачи/сдачи, брак, потери, готовый склад,
этикетки, отчеты и неизменяемый журнал движений.

Актуальный рабочий контекст, проверенные команды и статус чистого запуска
ведутся в [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md).

## Состав

Активные модули:

```text
cabochon_base
cabochon_manufacturing
```

`cabochon_base` содержит корневое меню, группы доступа, справочники, аудит и
защиту Cabochon-активностей.

`cabochon_manufacturing` содержит операции, складские зоны, мешки, внешний
приход, производственные заявки, выдачи/сдачи, брак, возврат брака, готовый
склад, корректировки, отчеты и этикетки.

## Установка

Текущая рабочая база:

```text
Prod
```

База Odoo должна быть создана заранее. Первый запуск модулей:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install_modules.ps1 -Database Prod -Install
```

Обновление после изменений:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install_modules.ps1 -Database Prod
```

### Безопасное обновление существующего сервера

Сначала проверьте релиз на свежей копии серверной базы вместе с filestore.
Сохраните предыдущий релиз отдельно **до замены исходников**. Скрипт не переносит
код на сервер и не сохраняет старый код: он обновляет базу под уже подключенный
к контейнеру каталог `addons`.

Docker-режим скрипта:

1. Определяет точный образ, сеть, пользователя, окружение и тома рабочего контейнера.
2. Создает временный контейнер обслуживания без опубликованных портов.
3. Останавливает рабочий контейнер и создает ZIP базы **с filestore**.
4. Проверяет наличие непустого `dump.sql` и `manifest.json`, сохраняет SHA-256.
5. Обновляет только два активных модуля, сохраняя журнал выполнения.
6. Только при коде завершения 0 запускает рабочий контейнер с новым Python-кодом.

Копии, контрольные суммы, сведения об образе и журналы сохраняются в `backups/`.
Путь можно изменить параметром `-BackupDirectory`. Они не должны попадать в Git.
Если к базе подключены другие процессы Odoo, интеграции или фоновые писатели,
остановите их отдельно: скрипт управляет только указанным контейнером.

```powershell
# Другой сервер/контейнер: выполняется на машине с доступом к его Docker.
powershell -ExecutionPolicy Bypass -File scripts\install_modules.ps1 -Database Prod -OdooContainer odoo19-web

# Локальный odoo-bin: службу остановить заранее; после успеха запустить вручную.
powershell -ExecutionPolicy Bypass -File scripts\install_modules.ps1 -Database Prod -OdooBin C:\odoo\odoo-bin.exe -Config C:\odoo\odoo.conf -DbHost localhost -ServiceStopped
```

Пароль берется из конфигурации Odoo либо переменной `ODOO_DB_PASSWORD`;
доступен также параметр `-DbPassword`. Не сохраняйте рабочие пароли в Git.
При нескольких сетях контейнера укажите `-DockerNetwork`.

**При ошибке рабочий контейнер остается остановленным.** Прочитайте журнал,
проверьте состояние базы и определите способ восстановления. Автоматического
отката нет: Odoo может фиксировать отдельные стадии обновления модулей.
Для отката нужны согласованные предыдущий код, база и filestore; одного возврата
Python-файлов недостаточно. Проверка ZIP не заменяет пробное восстановление.
После запуска проверьте вход работников, выдачу, отказ и сдачу.

### Изменения 19.0.2.37.0

- Статусы и подписи защищены на сервере; RPC-контекст не отключает защиту или аудит.
- Работник может отказаться от ожидающего его подтверждения документа без общего
  права редактирования. Документ возвращается менеджеру без движения материалов.
- Основные и дополнительные мешки занимают единый резерв. При отмене он снимается.
- Повторное выполнение мастеров прихода, возврата брака, выдачи и корректировки запрещено.
- Повторное накопление брака после полного возврата получает уникальный штрихкод.
- Готовые позиции объединяются с защитой конкурентных транзакций; новые дубли
  запрещены уникальным индексом. Внешний приход одинакового готового товара также
  увеличивает существующую позицию; возвращаемая карточка показывает ее ID.
- Нельзя вручную закрыть заявку с незавершенными сдачами или остатками у работника.
- В движении сохраняются фактический пользователь и покупатель готового товара.
- Нормы потерь фиксируются при создании движения. Для старых движений миграция
  сохраняет норму, известную **на момент обновления**, и отмечает ее как восстановленную.
  Исходную историческую норму, если ее не хранили, восстановить достоверно нельзя.
- Проценты брака/потерь в отчете считаются от общего выданного веса соответствующей
  заявки и работника. Отдельная операция задачи больше не получает ложные 0% из-за
  отличия ее ключа от полного маршрута. Проценты разных операций не являются
  самостоятельным учетом входного веса каждого этапа.
- Разделение документов, строк, отчетов и допусков по разрешенным компаниям усилено.
  Системные складские зоны остаются общими: независимые склады нескольких компаний
  требуют отдельной настройки и проверки бизнес-процесса.
- Добавлены индексы связей; выбор мешка использует резерв вместо загрузки всей истории заявок.

Перед обновлением проверьте конфликтующие резервы и дубли готовых позиций на копии:
при конфликте миграция/индекс прерывают обновление, не объединяя старые записи.
Даты старых подтверждений и веса существующих движений автоматически не исправляются.

### Новые инструменты

`Операционный учет → Отчеты → Контроль целостности` доступен администратору.
Он показывает отрицательные остатки, выданные мешки без владельца, подтверждения
без дат/авторов, выдачи без движений, движения у неподтвержденных документов,
несовпадение компаний движения и исходного мешка, остатки у работника при закрытой
заявке и дубли готового склада. Записи можно открыть из отчета. Это диагностика,
а не автоматическая корректировка или полная бухгалтерская сверка движений.

`Работа → Найти мешок по коду` открывает доступный пользователю мешок по штрихкоду
или точному ID. Поддерживается обычный сканер с вводом как с клавиатуры. QR/Code128
на этикетках по-прежнему скрыты согласно прежней настройке проекта.

### Регрессионные проверки

Тесты запускаются только на отдельной базе. `--http-port` должен быть свободен:

```powershell
docker exec odoo19-web odoo -d CabochonReviewTest -u cabochon_base,cabochon_manufacturing --stop-after-init --http-port 8099 --test-enable --test-tags /cabochon_manufacturing --db_host db --db_port 5432 --db_user odoo
```

В тестах проверяются обычные роли, отказ, защита статусов и аудита, однократное
списание, повторное накопление брака, резервы, историческая норма и база процентов.

`scripts/check_concurrency.py` дополнительно проверяет две независимые транзакции:
объединение готового остатка и конкуренцию основного/дополнительного резервов.
Он **фиксирует тестовые записи**, поэтому требует одноразовую базу с именем
`Cabochon*Test`. Запускать через `odoo shell`, передавая файл с UTF-8, как smoke.
Успех обозначается `CONCURRENCY_OK`; ожидаемые ошибки сериализации внутри повторов
не означают потерю данных.

Проверено 2026-09-06: 12 Odoo-тестов, чистая установка и smoke, конкурентные
сценарии, обновление старой копии с сохранением 26 мешков / 12260 г и 34 движений,
полный цикл скрипта обновления на отдельном контейнере и остановка при ошибке
создания бэкапа. Созданный скриптом ZIP восстановлен: остатки и движения совпали,
31 файл filestore проверен побайтово. Основная `Prod` не обновлялась.
Тестовые базы и контейнер удалены после проверок.

Следующие низкоуровневые команды не делают бэкап и не останавливают службу.
Для рабочего сервера используйте процедуру и скрипт выше:

```powershell
docker exec odoo19-web odoo -d CabochonReviewTest -i cabochon_base,cabochon_manufacturing --stop-after-init --db_host db --db_port 5432 --db_user odoo --db_password 123321 --log-handler odoo.tools.convert:DEBUG
docker exec odoo19-web odoo -d CabochonReviewTest -u cabochon_base,cabochon_manufacturing --stop-after-init --db_host db --db_port 5432 --db_user odoo --db_password 123321 --log-handler odoo.tools.convert:DEBUG
```

`odoo-bin` с `-i` для первой установки или `-u` для обновления.

## Старт с нуля

При чистой установке создаются меню, права, системные операции и складские
зоны. Бизнес-данные остаются пустыми: без мешков, заявок, выдач, сдач и
движений.

После установки нужно настроить пользователей и сотрудников, назначить группы
Cabochon, указать менеджеров зон `raw`, `prepared`, `semi_finished`,
`finished`, заполнить справочники и разрешенные операции работников.

Smoke-проверку запускайте только на временной базе, потому что сценарий создает
тестовые записи:

```powershell
docker exec odoo19-db createdb -U odoo CabochonSmoke
docker exec odoo19-web odoo -d CabochonSmoke -i cabochon_base,cabochon_manufacturing --stop-after-init --db_host db --db_port 5432 --db_user odoo --db_password 123321 --log-handler odoo.tools.convert:DEBUG
$OutputEncoding = [System.Text.UTF8Encoding]::new()
Get-Content -Raw -Encoding UTF8 scripts\smoke_zero_start.py | docker exec -i odoo19-web odoo shell -d CabochonSmoke --db_host db --db_port 5432 --db_user odoo --db_password 123321
docker exec odoo19-db dropdb -U odoo --if-exists --force CabochonSmoke
```

Успешный результат smoke-сценария:

```text
SMOKE_ZERO_START_OK
```

## Текущие правила учета

- Несколько исходных мешков разрешены только для операции `Трубы` и только с
  одинаковым годом и месяцем добычи.
- На формах сдачи остаток считается от выданного веса с учетом частичных сдач.
- Брак агрегируется по операции, форме, типу формы и цвету; размер при возврате
  брака выбирается вручную.
- Готовый склад объединяет вес по форме, типу формы, размеру и цвету; количество
  считается от эталонного веса размера.
